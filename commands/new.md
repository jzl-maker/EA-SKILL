# 命令: /ea new (新功能开发)

## 功能
进入新功能开发流程。**嵌入式聚焦**的两档分流：轻档直接改，标准档 brainstorm → plan → execute。避免轻量需求被重流程拖累，也避免重特性被轻流程带偏。

需求描述不准确 / 不规范时，在开发前插入**阶段 0 需求澄清**（与用户共同坐实需求再动手）。

## 触发
```
/ea new <功能描述>              # AI 推荐档位，用户确认
/ea new <功能描述> --light      # 强制轻档
/ea new <功能描述> --std        # 强制标准档（默认）

# 需求澄清（阶段 0）控制
/ea new <描述> --plan-only      # ⭐ 只做需求澄清，产出 requirement.md 后停下
/ea new <描述> --no-clarify     # 需求已明确，跳过阶段 0
/ea new <描述> --quick          # 澄清深度=快（≤3 题）
/ea new <描述> --deep           # 澄清深度=深度（9 维度全扫）
/ea new <描述> --doc <路径>     # 从文档提取需求（先跑 /ea doc）
```

| 参数 | 作用 |
|------|------|
| `--plan-only` | 只澄清 + 出方案，不进入编码。用于需求评审 / 立项前对齐 |
| `--no-clarify` | 跳过阶段 0，直接进档位流程 |
| `--quick` / `--deep` | 覆盖澄清深度（默认由档位自动推荐）|
| `--doc <路径>` | 用 `/ea doc` 解析出的文档内容作为需求输入源 |

## 两档总览

| 档位 | 适用 | 产出文件 | 时长 | 工作流 |
|------|------|---------|------|--------|
| **轻 light** | < 2h 工作量、单文件改动、bugfix、调参、简单逻辑 | `quick-plan.md` | ~5 min | `workflows/new-light.md` |
| **标准 standard**（默认）| 跨模块特性、新外设、需设计 | `brainstorm.md` + `milestones.md` | ~15 min | `workflows/new-standard.md` |

## 档位推荐启发式

| 信号 | 加分到 |
|------|--------|
| 描述 ≤ 30 字 / 关键词：修复/fix/调整/优化/改进/重命名 | 轻 |
| 关键词：实现/接入/集成/添加模块 | 标准 |
| 关键词：架构/系统/协议栈/状态机/重构 | 标准 |
| **涉及新外设/新芯片/时序/实时性**（嵌入式硬件维度）| 标准（强制硬件对齐阶段）|

**默认**: 标准档。

## 澄清深度启发式（阶段 0 用）

| 深度 | 问题数 | 适用 | 触发信号 |
|------|--------|------|---------|
| **快 quick** | ≤3（只问阻塞性歧义）| 描述完整、单点改动 | 轻档 / 描述含外设+时序+验收 |
| **标准 standard**（默认）| 5-10 | 常规新功能 | 标准档 |
| **深度 deep** | 9 维度全扫 + 方案对比 | 新外设 / 协议栈 / 系统级 | 关键词：协议栈/状态机/架构/新芯片 |

默认与档位联动推荐（轻→快，标准→标准，深度信号→深）；`--quick` / `--deep` 可覆盖。

## 执行流程

1. **【状态目录】** `get_state_dir()` → 不存在提示 `/ea init`
2. **【读 context】** 必须先读 `<STATE_DIR>/context.md`（芯片/外设/模块地图/保护区）——理解工程再规划
3. **【步骤号分配】** 读 `state.md` / `project-spec.md` 步骤表，取最大 S + 1
4. **【档位 + 澄清深度推荐】**（一次性给出、一次确认）
   - 命令带 `--light/--std` → 直接采用；带 `--quick/--deep` → 深度直接采用
   - 否则按启发式推荐两者，输出：
     ```
     🆕 新功能: <描述>
        分配步骤: S<N>
        推荐档位: <轻|标准>   理由: <一句话>
        澄清深度: <快|标准|深度>   理由: <一句话>
        其他档位: /ea new ... --light | --std
        跳过澄清: /ea new ... --no-clarify
        ━━━━━━━━━━━━━━━━━━━━━━━━━━━━
        输入 `继续` 采用推荐，或输入 `轻/标准`、`快/标准/深度` 改。
     ```
5. **【阶段 0: 需求澄清】** 除非 `--no-clarify` → 加载 `workflows/req-clarify.md` 执行
   - `--plan-only` → 澄清 + 方案完成后**结束**（不进编码）
   - 澄清结果若暴露硬件级 / 跨模块信号 → 提示升档（轻 → 标准），用户确认后改档
6. **【加载对应工作流】** 轻 → `new-light.md`；标准 → `new-standard.md`
7. **【按工作流执行】** 标准档含嵌入式硬件对齐阶段（外设/引脚/时序/实时性约束）
8. **【收尾】** 更新 `state.md`（下一步动作 = `/ea verify s<N>`），写入 `project-spec.md` 步骤表

## 公共规则

- **步骤编号**：`S<数字>`，废弃不复用
- **讨论目录**：`<STATE_DIR>/discussion/<YYYYMMDD>-<slug>/`
- **需求文件**：澄清产出 `requirement.md`，是后续 brainstorm / quick-plan 的输入，不重复分析需求
- **修改红线**：开发过程中所有文件改动遵守 SKILL.md 红线——保护区文件禁随意改、增量修改、改动给 diff
- **强制约束**：流程未完成禁止 `/ea verify` / `/ea record`
- **禁止猜测需求**：阶段 0 若发现歧义，必须提问；禁止用「按常规理解」蒙混过去

## 输出格式（确认阶段后）

```
🆕 S<N>: <功能描述>
档位:   <轻|标准>      澄清深度: <快|标准|深度>
需求:   <STATE_DIR>/discussion/<YYYYMMDD>-<slug>/requirement.md
讨论ID: <YYYYMMDD>-<slug>
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
<工作流首阶段提示，由对应 workflow 文件给出>
```

## 设计原则
- **superpower 精神**：先澄清需求 → 再 brainstorm → 再 plan → 再 execute
- **需求先行**：模糊需求先坐实再规划，嵌入式返工成本极高（改引脚=改板）
- **两档分流**：轻量需求不被重流程拖累；嵌入式硬件维度进标准档
- **先 context 后动手**：AI 对老工程有上下文感知再开发
- **增量约束**：全程给 diff，禁全盘重写
