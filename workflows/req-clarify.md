# 工作流: 需求澄清（req-clarify）

> 适用：`/ea new` 阶段 0 —— 用户需求描述不准确 / 不规范 / 有歧义时，先与用户共同把需求坐实，再进开发。
> 产出：`<STATE_DIR>/discussion/<YYYYMMDD>-<slug>/requirement.md`
> 由 `commands/new.md` 调用；也可 `--plan-only` 单独跑（只澄清、不开发）。

## 核心理念

**需求不清则方案无意义**。嵌入式开发的返工成本极高（改引脚要改板、改协议要改对端、改实时性要重排任务），
所以宁可在这里多问 5 分钟，也不要在烧录后才发现理解错了。

原则：
1. **AI 主动提问，不猜** —— 歧义处必须问，禁止用「按常规理解」蒙混
2. **每题给推荐答案** —— 用户可以直接采纳，不必每次都思考；推荐必须附一句话理由
3. **分批问，不轰炸** —— 每轮 ≤4 题；先问阻塞性的，再问细节
4. **即问即落盘** —— 每轮答完立刻写入 `requirement.md`，防上下文丢失

## 前置

- 已读 `<STATE_DIR>/context.md`（芯片/外设/模块地图/保护区）——很多问题的候选答案来自这里，不用问用户
- `commands/new.md` 已分配步骤号 `S<N>`

## 流程

```
1. 输入源判定      自由文本 / --doc <路径> / 对话补充
   ↓
2. 歧义扫描        按 9 维度扫描缺失项 → 生成候选问题
   ↓
3. 分批问答        结构化题 → AskUserQuestion；开放题 → 文本
   ↓
4. 需求复核        AI 复述 → 用户确认/修正 → 锁定
   ↓
5. 方案生成        2-3 候选方案（含硬件可行性）→ 用户选定
   ↓
6. 落盘            requirement.md + decisions.md
```

## 阶段 1: 输入源判定

| 输入源 | 处理 |
|--------|------|
| 自由文本（`/ea new "..."`）| 直接进歧义扫描 |
| 文档（`--doc <路径>`）| 先 `/ea doc <路径>` 提取 → 再扫描 |
| 一句话口头描述 | 扫描出的问题会偏多，深度档自动上调建议 |

**先做的事**：用一句话复述你理解到的需求，让用户先纠正方向性错误——方向错了问再多细节都白费。

> 💡 若描述已包含「做什么 / 用什么外设 / 什么时序 / 怎么算验收」，可直接跳过澄清（`--no-clarify`）。

## 阶段 2: 歧义扫描（9 维度）

对每个维度判定：**已明确 / 缺失 / 矛盾**。只对「缺失」和「矛盾」的维度提问。

| # | 维度 | 要问清楚什么 | 缺失的后果 |
|---|------|-------------|-----------|
| 1 | **功能边界** | 做什么、不做什么、触发条件、异常时行为 | 改动范围失控，做多了或做漏了 |
| 2 | **芯片 / 主频** | 现有 MCU 型号、主频、算力是否够 | 方案超算力，编码完才发现跑不动 |
| 3 | **外设 / 引脚** | 需要哪些外设、引脚是否冲突、是否碰 SWD | 改板 / 改硬件，返工成本最高 |
| 4 | **时序 / 实时性** | 采样周期、响应延迟上限、允许抖动 | 硬实时做成软实时，现场失效 |
| 5 | **通信协议** | 接口（UART/SPI/I2C/CAN/USB）、帧格式、波特率、超时重传 | 与对端联调不通 |
| 6 | **资源余量** | Flash/RAM 余量、栈深度（可衔接 `/ea size`）| 编译超限 / 运行栈溢出 |
| 7 | **供电 / 低功耗** | 是否低功耗、唤醒源、功耗指标 | 电池产品续航不达标 |
| 8 | **环境 / 可靠性** | 温度范围、看门狗、异常恢复策略 | 现场死机无法自恢复 |
| 9 | **验收标准** | 「能用」→ 可测的具体判据（衔接 `/ea test`）| 无法判定做完了没有 |

**候选答案来源优先级**：`context.md` 已记录 → 不问，直接引用；工程代码可查证 → 查完再问；否则 → 必须问用户。

## 阶段 3: 分批问答（混合式）

### 结构化问题 → `AskUserQuestion` 工具

适合「答案是可枚举的选项」的问题。用法约束：
- 每次调用 **≤4 题**，每题 **2-4 个选项**
- **推荐项放第一位**，label 加 `（推荐）` 后缀，`description` 写理由
- 用户可选「Other」自由输入

示例（时序 / 通信维度）：
```
Q: 数据上报周期？
  A. 100ms（推荐）— 现有 Timer3 已配 1ms 时基，分频即得，无需新增外设
  B. 10ms — 需提高 Timer3 中断频率，注意中断内耗时
  C. 1s — 最省电，但实时性差
```

### 开放性问题 → 文本列出

适合「需要用户描述场景/期望行为」的问题：
```
请补充（可直接回答编号，不确定的写「不确定」）：
  Q5. 通信中断后，期望的行为是？（自动重连 / 报错停机 / 点亮故障灯）
  Q6. 设备断电重启后，之前采集的数据要保留吗？
```

### 分轮策略

| 轮次 | 内容 |
|------|------|
| 第 1 轮 | 阻塞性问题（不回答就无法写代码的）|
| 第 2 轮 | 硬件约束问题（外设/引脚/时序）|
| 第 3 轮 | 边界与异常（环境/可靠性/验收标准）|

每轮答完 → **立即把结果追加写入 `requirement.md` 第 3 节**，再进下一轮。

## 阶段 4: 需求复核

AI 输出结构化复述，请用户确认：

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📋 需求复述（S<N>）
功能: <一句话>
硬件: <芯片/MCU + 新增外设 + 引脚>
时序: <周期 / 延迟 / 实时性要求>
协议: <接口 + 帧格式>
验收: <可测判据>
不做: <明确排除的范围>
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
输入 `确认` 锁定 / `修正: <...>` 直接改正 / `补充: <...>` 追加
```

用户 `确认` 后需求**锁定**，后续改动写入 `decisions.md`。

**升档检查**：若复核时发现以下信号 → 提示用户升档为标准档：
- 涉及新外设接入 / 引脚冲突 / 中断向量表改动（保护区）
- 跨 ≥3 个模块 / 需要状态机 / 协议栈
- 有硬实时约束

## 阶段 5: 方案生成

按 `requirements` 出 2-3 个候选方案（轻档可只给 1 个）：

```markdown
### 方案 A: <名字>
- 思路 / 涉及文件 / 优点 / 缺点·风险 / 预估工作量 / 硬件占用

### 方案 B: <名字>（同上）
```

推荐方案附一句话理由。提示：`继续` 采用 / `A`/`B` 改选 / `补充: <...>` / `取消`。

> 标准档的方案对比可并入 `new-standard.md` 的 brainstorm 阶段——此处不重复展开，只给初步候选。
> 若 `--plan-only` 单独运行，则此阶段必须给出完整方案。

## 阶段 6: 落盘

1. 写 `<STATE_DIR>/discussion/<YYYYMMDD>-<slug>/requirement.md`（模板见 `templates/requirement.md`）
2. `decisions.md` 追加：需求锁定时点 + 选定方案 + 关键取舍
3. 输出：

```
🧭 需求澄清完成（S<N>，深度: <快|标准|深度>）
📄 <STATE_DIR>/discussion/<...>/requirement.md
❓ 提问: <N> 个（结构化 <a> / 开放 <b>）
🎯 方案: <选定方案名>   ⚠️ 未决项: <N> 条
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
下一步:
  --plan-only 模式 → 结束。要开发时执行 /ea new <描述> --no-clarify
  正常模式        → 交给档位工作流（new-light / new-standard）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 跳过 / 中断

| 场景 | 行为 |
|------|------|
| 需求已明确 | `--no-clarify` 跳过整个阶段 0 |
| 用户答「不确定」 | 记入 `requirement.md` 第 4 节「未决 / 风险」，不阻塞；评审时提醒 |
| 用户中途取消 | 已问部分仍落盘（`requirement.md` 标记 `状态: 未完成`），便于下次续问 |
| 与现有 `context.md` 矛盾 | 立即指出矛盾点，请用户裁决（不自行选一个）|

## 相关文件
- `commands/new.md` — 入口（阶段 0）
- `templates/requirement.md` — 产出模板
- `templates/context.md` — 候选答案来源（先读）
- `workflows/new-standard.md` — 标准档（消费 requirement.md）
- `workflows/new-light.md` — 轻档（消费 requirement.md）
- `commands/doc.md` — `--doc` 输入源解析
